# Technical Decisions — OpenAPI Documentation for NestJS

_Subprojects in scope:_

- `nestjs-project/` — backend: generates and exposes the OpenAPI specification. All TDs in this document apply here.
- `next-frontend/` — frontend: **no open decision in this document.** TD-02 defines a stable artifact (`openapi.json`) whose consumption by the frontend (TS client codegen) is future work; a dedicated TD will be opened when the frontend actually integrates the spec.

---

## TD-01: OpenAPI Documentation Tooling

**Scope:** Backend

**Trigger:** Need to document the NestJS REST API via OpenAPI 3.x, with minimal maintenance friction and alignment with the already-decided stack (class-validator + class-transformer — phase-02-auth/TD-06).

**Context:** The NestJS 11 project currently publishes no API documentation. Prior decisions fixed `class-validator` + `class-transformer` for validation (phase-02-auth/TD-06) and defined the standard error envelope (phase-02-auth/TD-07). The choice of OpenAPI tooling needs to preserve these decisions — replacing them would have a cascading effect on all DTOs already implemented in phase 02. The decorators-vs-type-introspection trade-off is the central one.

**Options:**

### Option A: `@nestjs/swagger` (official)
- Official NestJS package, based on decorators (`@ApiProperty`, `@ApiResponse`, `@ApiTags`) and an OpenAPI generator built on `DocumentBuilder`. Supports a CLI plugin (`nest-cli.json` → `plugins`) that does **automatic introspection** of DTOs with `classValidatorShim: true`, reducing explicit decorators to a minimum.
- **Pros:** Native integration with `class-validator`/`class-transformer` (already in the stack). Low learning curve for teams with NestJS experience. CLI plugin eliminates ~80% of the boilerplate once configured. Mature ecosystem: embedded Swagger UI, ready-made JSON/YAML export, auth scheme support (Bearer/JWT) out-of-the-box. `@nestjs/swagger ^11` is compatible with the installed `@nestjs/core ^11.0.1`.
- **Cons:** Requires some additional annotation for complex responses, polymorphism, and per-status variations. The spec depends on runtime metadata (decorators) — there is no "pure type-driven" mode without the CLI plugin.

### Option B: Nestia (`@nestia/core` + `@nestia/sdk`)
- Alternative type-driven toolkit: generates OpenAPI from **pure TypeScript types** (preferably `interface`), without `@ApiProperty`. Includes client SDK generation and its own validator (`typia`) ~20,000× faster than `class-validator`.
- **Pros:** Zero-decorator schema generation. Built-in SDK codegen. Superior runtime performance (typia). Active community, dedicated docs.
- **Cons:** **Conflicts with the stack already decided in phase-02-auth/TD-06 (class-validator + class-transformer):** Nestia's benefit requires adopting `typia` as the validator, which is a re-platform — incompatible with keeping `class-validator` in the already-implemented phase 02. DTOs would need to be rewritten as interfaces. Smaller adoption (relative to the official package). New learning curve.

### Option C: Manual OAS authoring (hand-written openapi.yaml/json)
- Keep the `openapi.yaml`/`openapi.json` file versioned and hand-edited, with no automatic generation from the code.
- **Pros:** Full control. Spec not coupled to the code.
- **Cons:** Manual maintenance diverges from the real code — high risk of a stale spec. No automatic detection of drift between DTO and contract. Work grows proportionally with the API.

**Recommendation:** **Option A (`@nestjs/swagger`)** — it is the only option that preserves the prior decisions (`class-validator` in phase-02-auth/TD-06) without a re-platform; the CLI plugin with `classValidatorShim: true` leverages the existing `class-validator` decorators to infer schemas, keeping boilerplate low. Nestia has real technical merit, but the validation-stack migration cost makes it unviable without an upstream decision to supersede TD-06. Manual authoring is ruled out.

**Decision:** A (@nestjs/swagger + CLI plugin)
**Libraries:** @nestjs/swagger

**Revisions:**

- 2026-05-12 — Clarifies that the CLI plugin (`classValidatorShim: true`) covers only DTO schema inference from `class-validator`; operation documentation, responses typed per status code, error contracts (aligned with the phase-02-auth/TD-07 envelope), and examples require explicit decorators (`@ApiOperation`, `@ApiResponse`, `@ApiBody`, `@ApiParam`, `@ApiQuery`, `@ApiExtraModels`). _Rationale:_ the openapi.json generated by the current bootstrap is generic — without parameter details, per-status response schemas, or error contracts — because the installed baseline relied only on automatic introspection. This revision establishes that enrichment via explicit decorators is part of the chosen Option A, not work outside the TD's scope.

## TD-02: OpenAPI Spec Artifact Strategy

**Scope:** Cross-layer

**Trigger:** Define how the OpenAPI spec is exposed to consumers — humans (interactive exploration) and machines (future FE client codegen).

**Context:** `@nestjs/swagger` (TD-01, Option A) allows two modes of publishing the spec: **runtime** (Swagger UI + JSON endpoint served by the Nest application) and **static artifact** (`openapi.json` file generated at build/script time and committed or published in CI). The choice affects how the (future) frontend consumes the contract: if the spec only exists at runtime, codegen requires the API to be up; if it exists as a file, codegen runs offline in any CI. Since `next-frontend` doesn't integrate the spec yet but will, the decision is cross-layer — the artifact is the point of contact between the subprojects.

**Options:**

### Option A: Runtime-only (Swagger UI + JSON endpoint, no file)
- `SwaggerModule.setup('api/docs', app, document)` mounts the UI at `/api/docs` and the JSON at `/api/docs-json`. No file is generated/committed.
- **Pros:** Minimal setup (one block in `main.ts`). Spec always reflects the running code — zero risk of drift between file and runtime. No additional build step.
- **Cons:** FE codegen requires the API to be running at that moment (CI needs to bring up the backend or point at a stable instance). No contract history in PR diffs — schema changes are invisible until someone compares specs at runtime.

### Option B: Static artifact only (generate `openapi.json`, no runtime UI)
- An `npm run openapi:gen` script instantiates the NestJS app in "build-only" mode, calls `SwaggerModule.createDocument`, serializes `JSON.stringify(document)` into `openapi.json` (or `<backend-subproject>/openapi.json`), and exits. Runtime UI disabled. File committed or published in CI.
- **Pros:** Versioned contract — changes appear as a PR diff. FE codegen runs offline. Breaking-change auditing is easier.
- **Cons:** No interactive UI for developers and QA. The spec can go stale if a developer forgets to run the script before committing — requires a hook or CI step to guarantee freshness.

### Option C: Both — runtime UI + static artifact
- Keeps `SwaggerModule.setup('api/docs', ...)` at runtime **and** runs an export script to `openapi.json` at build/CI time. UI for humans, file for codegen.
- **Pros:** Covers both use cases without compromising either. FE has a stable artifact; devs/QA get an interactive UI. Drift between file and runtime is detectable via PR diff (a stale `openapi.json` is a visible diff).
- **Cons:** Two surfaces to maintain (one runtime config line + one npm script). Marginally more complex than A or B alone.

**Recommendation:** **Option C (Both)** — the marginal cost over Option A is just one npm script (~15 lines), and the benefit is a correct foundation for future FE integration (offline codegen) without losing the interactive UI dev/QA use. Option B alone penalizes the dev/local development experience; Option A alone compromises the future codegen pipeline. Combining them dominates.

**Decision:** C (Runtime UI + exported openapi.json)

## TD-03: Production Exposure Policy for Swagger UI

**Scope:** Backend

**Trigger:** Decide whether the interactive Swagger UI stays exposed in production (and under what conditions).

**Context:** The Swagger UI in production is useful (living documentation for integrators) but increases attack surface: it enumerates every endpoint, accepted parameters, response formats — useful for reconnaissance. Today the project has no requirement for a public third-party API; it's a platform oriented around its own first-party frontend (`next-frontend`). The decision is a policy call, not a technical one — which side of the trade-off to prioritize.

**Options:**

### Option A: Always exposed (all environments, no auth)
- `SwaggerModule.setup` called unconditionally in `main.ts`. `/api/docs` accessible from any origin in prod.
- **Pros:** No conditionals. Documentation always available for occasional integrators.
- **Cons:** Easier reconnaissance for attackers. A public spec can expose internal endpoints not intended for external consumers (admin, debug). Doesn't align with phase 02's defensive posture (rate limiting, refresh rotation).

### Option B: Dev/staging only (disabled in prod via env)
- `if (process.env.NODE_ENV !== 'production') { SwaggerModule.setup(...) }` or a dedicated `SWAGGER_ENABLED` flag. In prod, `/api/docs` returns 404. `openapi.json` (TD-02) remains available as a repo/CI artifact for anyone who needs it.
- **Pros:** Minimizes prod surface. Doesn't block legitimate external consumption — the committed file covers that. Aligned with the defensive stance already established (phase-02-auth TD-08 — throttler).
- **Cons:** Developers need to consult staging or the committed file to inspect the prod contract. During prod troubleshooting, there's no clickable UI (needs to be replicated locally).

### Option C: Always exposed with basic auth in prod
- `SwaggerModule.setup` always called; in prod, extra middleware protects `/api/docs` with Basic Auth (credentials via env). Dev/staging unprotected.
- **Pros:** Documentation available to authorized partners in prod. Anonymous attackers can't enumerate the API.
- **Cons:** Another credential to manage/rotate (more stuff in `.env`). Basic auth isn't robust on its own. Adds specific middleware code. For a project with no clear public-API use case, this is over-engineering.

**Recommendation:** **Option B (Dev/staging only)** — aligns with the defensive posture already established in phase 02 and doesn't compromise legitimate consumers (the `openapi.json` committed under TD-02 fulfills the role of "spec inspectable outside the UI"). Reopening as Option A or C is trivial in the future if a public-API use case emerges.

**Decision:** B (Dev/staging only via env flag)
