  - **MSW-architecture tension resolved via a 2-pass job design.** Every existing `tests/*.e2e-spec.ts` file assumes the upstream `nestjs-api` is faked server-side via MSW (`MSW_ENABLED=true`, a hard rule in `next-frontend/CLAUDE.md`'s § E2E architecture) — running them against a real backend would be structurally wrong (their assertions are keyed to MSW fixture values like "Alice"/"pub123", never real DB data). The new `.github/workflows/full-stack-e2e.yml` job therefore runs Playwright **twice**: Pass 1 = the existing suite with `MSW_ENABLED=true` (unchanged, still faked); Pass 2 = only the 3 new `tests/full-stack/*.e2e-spec.ts` journeys with `MSW_ENABLED` unset, against the real stack. The env var is read once at `next-frontend`'s server boot (`instrumentation.ts`), so the dev server process is stopped and restarted between passes.
  - **CI job reuses the dev `Dockerfile.dev` + `compose.yaml` setup, not SI-07.5's production Dockerfiles** — deliberate choice: the proven `MSW_ENABLED=true npm run dev` mechanism this whole session has relied on is what the existing suite needs, and `next.config.ts`'s `output: "standalone"` production build likely prunes `mocks/` (only reachable via an `MSW_ENABLED`-conditional dynamic import) since standalone's dependency tracing may not follow that conditional path — untested, unnecessary risk for a job about E2E correctness, not deployment-readiness (SI-07.5 already separately verified the production images build cleanly on their own).

Mailpit exposes a REST API on port 8025; `signup-to-login.e2e-spec.ts` and `social-interactions.e2e-spec.ts` both poll `GET /api/v1/messages`, fetch the matching message's body via `GET /api/v1/message/{ID}`, regex-extract the real confirmation URL, and hit it directly via Playwright's `request` fixture — genuinely exercising the real email pipeline, verified by manually replaying the exact same sequence via `curl` against the running dev stack before trusting the Playwright version.
  - **Real bug found and fixed during verification (not a test-authoring mistake to shrug off):** `components/auth/login-form.tsx`'s `onSubmit` only calls `router.refresh()` on success, never `router.push()` — the `/login` page has no redirect-away-after-login logic anywhere (checked `app/(auth)/login/page.tsx` directly). Every existing MSW-based spec's `loginAsXxx` helper already works around this by immediately `page.goto()`-ing to wherever it actually wants to test, right after waiting for the login response — my first draft of the 2 new specs incorrectly assumed an automatic redirect and failed on `toHaveURL(/\/$/)`. Fixed by following the same established pattern (wait for the login response, then navigate manually) rather than treating this as a product bug to fix — it's consistent, pre-existing, intentional-by-omission app behavior that this whole session's test suite has quietly worked around from day one.
  - **Second real bug, trivial:** `getByRole("button", { name: "Like" })` in `social-interactions.e2e-spec.ts` hit a strict-mode violation — substring-matches "Like comment" too (Playwright's default `name:` matching is substring, not exact). Same bug class as an earlier fix this phase (SI-07.4b's account-menu locator). Fixed with `{ exact: true }`.
